这个方向的目标，不是让 Unity 运行时直接跨项目加载资源，而是让 Locus 在当前项目会话里，显式读取另一个项目的资产上下文，并把它注入给 Agent。

建议的交互形式：

```text
#B:Assets/Prefabs/Hero.prefab
```

或者等价的“项目作用域 + 资产路径”形式：

```text
#B + Assets/Prefabs/Hero.prefab
```

在这个设计里：

- `B` 是目标项目标识
- `Assets/...` 是该项目内部路径
- 当前会话仍然属于 A 项目
- Locus 在发送消息前，到 B 项目的资产索引中解析该路径
- 然后把解析后的资产信息，以只读引用的形式注入到 A 项目的聊天上下文

## 定位

这是一种**跨项目只读引用**能力，不是 Unity 运行时引用能力。

它解决的问题是：

- 在 A 项目里与 Agent 讨论功能时，直接引用 B 项目的 Prefab、Scene、Material、Script 等作为上下文
- 做跨项目对照、迁移、复用分析
- 让 Agent 在同一条会话里理解“当前修改目标在 A，但参考实现位于 B”

它不直接解决的问题是：

- 让 A 项目在 Unity 里直接依赖 B 项目的资源
- 自动把 B 的资源导入、挂载或打包到 A

如果要让 A 真正使用 B 的资源，仍然需要额外的挂载、包引用或导入流程。

## 为什么这个方向可行

Locus 当前已经具备三块关键基础：

- 聊天输入侧已经支持结构化资产引用和附件注入
- 资产索引按 Unity 项目独立存储，每个项目都有自己的 `Library/Locus/locus.db`
- 消息发送链路已经支持把资产引用作为结构化附件传给后续处理流程

因此，缺失的并不是“资产引用机制”，而是“跨项目寻址层”。

## 建议语法

推荐把跨项目引用设计成显式作用域语法：

```text
#B:Assets/UI/Login.prefab
#B:Packages/com.game.shared/Runtime/HeroConfig.asset
```

设计原则：

- 必须一眼看出目标项目不是当前工作区
- 必须与现有普通路径引用区分开
- 必须能稳定拆出 `project scope` 与 `asset path`

不建议继续沿用“当前工作区路径即默认路径”的隐式解释方式来兼容跨项目，因为这会让解析与预览链路变得含混。

## 行为模型

在 A 项目会话中输入：

```text
参考 #B:Assets/Prefabs/Hero.prefab 的做法，实现一个简化版本
```

系统应执行以下过程：

1. 解析 `#B:Assets/Prefabs/Hero.prefab`
2. 将 `B` 解析为某个已知项目的 `workspaceId / projectRoot`
3. 在 B 的资产索引中查找对应路径
4. 读取可注入内容
5. 生成结构化附件，连同用户消息一起发送

Agent 最终拿到的是：

- 当前项目 A 的会话上下文
- 来自 B 项目的只读资产引用内容

这样 Agent 可以：

- 读取 B 的资产结构
- 把 B 作为参考实现
- 输出面向 A 的修改建议

## 数据模型建议

当前资产附件只包含路径和类型，足够表示“当前工作区资源”，但不足以表示“别的项目里的资源”。

建议扩展为：

```ts
interface AssetRefAttachment {
  workspaceId: string;
  projectLabel?: string;
  path: string;
  kind: "asset" | "sceneObject" | "knowledge";
  name?: string;
  typeLabel?: string;
  source?: "unity" | "manual";
}
```

关键变化：

- `workspaceId`：决定该路径在哪个项目下解析
- `projectLabel`：保留用户输入中的项目别名，如 `B`
- `path`：项目内相对路径，不再默认绑定当前工作区

## 前端改造点

### 1. 输入解析

聊天输入需要识别跨项目作用域引用：

- 解析 `#B:Assets/...`
- 或解析 `#B + 路径` 这种两段式输入

建议在现有资产引用提取逻辑之前，先做一层“项目作用域 token”解析，生成结构化引用对象，而不是仅仅把它当纯文本保留到发送阶段。

### 2. Mention / 选择器

如果要把体验做完整，输入 `#B:` 后应切换到 B 项目的资产搜索上下文，而不是继续搜索 A。

理想交互：

- 输入 `#B:`
- 弹出 B 项目的资产搜索结果
- 选择后写回 `#B:Assets/...`

### 3. 附件展示

资产附件区应显示来源项目，例如：

- `B / Assets/Prefabs/Hero.prefab`
- `B / Packages/com.game.shared/...`

这样用户能明确知道上下文来自哪个项目。

## 后端改造点

### 1. 项目注册表

需要有一层“已知项目列表”或“项目别名映射”：

- `B -> workspaceId`
- `workspaceId -> projectRoot`

这层数据不应依赖当前 `workingDir`，而应来自桌面端维护的项目目录列表或显式配置。

### 2. 按项目解析资产

现有很多资产命令默认基于当前工作区解析路径。跨项目引用之后，需要支持：

- 给定 `workspaceId`
- 给定 `path`
- 在对应项目根和对应 `locus.db` 下完成搜索、预览与注入

### 3. 注入载荷

给 Agent 的注入内容要保留来源项目信息，例如：

- 来源项目：B
- 资产路径：`Assets/Prefabs/Hero.prefab`
- 解析摘要 / YAML 结构 / 关键引用信息

这样模型不会误以为该资产天然属于当前 A 项目。

## 与“真实跨项目复用”的关系

这条能力应该作为第一层。

第一层：

- `#B:Assets/...`
- 只读
- 给 AI 用
- 不改变 Unity 项目结构

第二层才是：

- 挂载 B 到 A 的 `Assets/` 或 `Packages/`
- 或执行导入 / 复制
- 让 Unity 运行时与编辑器真正可用

这两层不应混在一起。前者解决“理解和参考”，后者解决“工程落地和可运行”。

## 推荐落地顺序

### 阶段一：只读跨项目引用

先支持：

- `#B:Assets/...` 语法
- 项目别名解析
- 结构化附件增加 `workspaceId`
- 按目标项目读取预览与注入内容

这一阶段就已经能满足大部分“把 B 作为参考上下文”的需求。

### 阶段二：跨项目浏览与选择

补齐体验层：

- `#B:` 后的资产搜索
- 选择器中的项目来源展示
- 最近项目 / 常用项目的快速切换

### 阶段三：从只读引用升级到工程落地

在需要时增加：

- 挂载到 `Assets`
- 挂载到 `Packages`
- 导入 / 拷贝工作流

## 风险与边界

### 1. 项目别名歧义

`B` 必须稳定映射到唯一项目，不能依赖用户临时记忆。

### 2. 索引过期

如果 B 的 `locus.db` 已经落后于磁盘状态，需要显式提示，而不是静默降级。

### 3. 同路径不同项目

`Assets/Prefabs/Hero.prefab` 在 A 和 B 中都可能存在。  
因此跨项目引用必须始终保留项目作用域，不能在中途退化为裸路径。

### 4. 不要伪装成“已导入到 A”

Agent 拿到 B 的上下文，不等于 A 已经拥有这个资产。  
注入文案和前端展示都应明确这是“外部项目只读参考”。

## 结论

`#B:资产路径` 这条设计方向是可行的，而且比“先做多项目统一工作区”更适合作为第一步。

它的正确定位是：

- 不是运行时跨项目依赖
- 不是 Unity 资产自动挂载
- 而是**跨项目只读上下文引用**

只要把“项目作用域”补到输入解析、附件模型、后端路径解析和注入载荷这四层，这个能力就可以稳定落地。
